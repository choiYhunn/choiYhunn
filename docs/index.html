03 / Research case study

CAN-FD: 평균 부하가 같으면 타이밍도 같을까?

2026 한국자동차공학회 추계학술대회 8페이지 Full Paper 제출. 공동저자. 연구의 핵심 성과는 특정 신호 패킹 전략을 우승자로 선정한 것이 아니라, 평균 점유율만으로 타이밍 조건의 동등성을 보장할 수 없다는 검증 방법론을 실험으로 구체화한 것이다.

≈37 μs초기 중간 부하 B–C 지터 차이
0.95 %p238→242 μs 조건의 점유율 감소
+48.1 μs같은 조건에서 지터 증가

문제 정의와 측정 경계

Renesas RA6M5 기반 Control TX / Background TX / RX의 3노드 구성과 PCAN-USB FD Listen-Only 추적을 사용했다. nominal 500 kbit/s, data 2 Mbit/s 설정에서 5 ms 주기의 제어 프레임 0x100 도착 간격 표준편차를 지터로 정의했다. 이는 절대 단방향 지연, PWM edge, 모터 응답시간과 동일한 지표가 아니다.

세 가지 패킹과 숨은 교란 변수

A는 8/8/16B 프레임을 분산 전송하고, B는 같은 주기끼리 32B로 묶고, C는 64B로 완전히 패킹했다. 초기 중간 부하 조건에서 A/B/C 지터는 각각 30.22/61.61/24.78 μs였다. 하지만 평균 부하를 맞추는 과정에서 배경 트래픽 gap도 A≈240, B≈235, C≈238 μs로 달라졌다. 따라서 처음 관찰한 B–C 약 37 μs 차이를 패킹 자체의 인과효과라고 주장할 수 없었다.

공통 조건 재측정

배경 gapA 지터B 지터C 지터

공통 생성기 입력에서는 처음의 큰 전략별 차이가 안정적으로 재현되지 않았다. 그렇다고 패킹의 타이밍 효과가 0이라고 증명한 것도 아니다. 특히 중간 조건에서는 반복 간 변동이 남았다.

더 강한 반례: 238→242 μs

전략 A에서 background gap 238 μs의 reconstructed occupancy는 약 63.75%, 지터는 25.49 μs였다. 242 μs에서는 점유율이 약 62.80%로 오히려 낮아졌지만 지터는 73.57 μs로 증가했다. 평균 부하라는 단일 스칼라가 프레임의 시간적 배열을 설명하지 못한다는 점을 보여준다. 보드 리셋과 측정 순서 변경을 포함한 별도 반복 검증은 A 전략의 일부 gap에 대해서만 수행했다.

배운 점. 보기 좋은 차이를 보존하는 것보다, 그 차이를 만들어낸 비교 조건이 공정한지 검증하는 것이 더 중요하다. 관측된 교대 패턴과 상대 위상에 대한 설명은 가설이지 입증된 물리적 원인이 아니다.

기여: Python trace 분석·QC, 비교 조건 감사, 결과 해석·보고서·발표 정리. 팀 전체 펌웨어 구현을 개인 단독 성과로 주장하지 않는다.

04 / Autonomous systems case study

AMET 2026: 빠른 모델보다 안정적인 폐루프

4위예선
3위결선
15 Hz최종 팀 제어 루프

Raspberry Pi 5 / Ubuntu 24.04 / ROS2 Jazzy 환경에서 camera·LiDAR → ONNX 도로 분할 → BEV 주행 가능 영역 → 21개 freespace arc → 조향·속도 제어로 이어지는 팀 시스템을 통합·검증했다. 최종 현대모비스상(우수상), 결선 3위는 사용자 확인 결과다.

도로 밖으로 회피하는 문제 — PR #20

단순히 장애물을 피해 열린 공간을 선택하면 그 방향이 도로 밖일 수 있었다. road-only arc가 가리키는 진행 방향과 cone-aware 후보가 충돌할 때, 허용 가능한 자유거리 범위 안에서 도로 방향 후보를 재평가하는 방식을 실험했다. 시뮬레이터 A/B에서는 개선이 관측됐지만 특정 실차 cone5 사고를 해결했다고 주장하지 않는다. 해당 로그에서 road-guide 활성화가 0회였기 때문이다.

조향 지연을 가정하고 검증 — PR #29

15 Hz에서 1프레임은 약 67 ms, 2프레임은 약 133 ms다. 개발용 지연 주입 도구로 조향 명령을 N프레임 늦게 적용하는 실험을 구성하고 속도 × 지연 매트릭스를 비교했다. 느리게 달린다고 항상 더 안정적이지 않았고, 2프레임 예측 보정이 일부 조건에서 효과적이더라도 실제 액추에이터 지연을 계측하지 않은 상태에서 고정 lead를 배포하는 것은 위험하다고 판단했다. 이 후보는 최종 팀 메인에 반영된 검증 완료 기능이 아니다.

개인 YOLO 후보를 최종 배포하지 않은 이유

주황색 차선 데이터의 직접 라벨링, Roboflow 데이터셋 버전 관리, Colab YOLO26n 학습, ONNX 내보내기, Raspberry Pi 추론 실험을 수행했다. 그러나 직접 픽셀 기반 후보는 검토 당시 추론 p50 약 374 ms로 제어 루프 예산을 크게 초과했다. 모델 정확도만으로 시스템 채택을 결정할 수 없다는 점을 확인하고 최종 팀 구성과 구분해 기록했다.

최종 결과. 팀 차량은 결선에서 직선 구간의 6개 라바콘 슬라럼을 모두 통과했다. 대회 성과는 팀 성과이며, 개별 PR과 개인 실험은 기여 범위를 분리한다.
05 / AI systems case study

AI Shared Brain: 여러 모델 사이에서 현재 상태를 잃지 않는 법

ChatGPT, Claude, Codex 등 여러 도구를 병행할 때 생기는 문제는 단순히 맥락 길이가 아니다. 최신 결정이 오래된 대화에 덮이거나, 검색 실패가 데이터 소실로 오인되고, 동시 편집이 충돌하는 문제가 있었다.

상태와 근거를 나눈 구조

현재 상태(L0), 프로젝트별 정본(L1), 기술 지식과 의사결정 이력(L2), 과거 대화 원문(L3)을 분리했다. 질문에 필요한 최소 자료만 읽고, 정확한 사실은 프로젝트 정본과 원본 소스에서 검증한다. Git blob/commit 기반 OCC는 같은 파일에 대한 오래된 편집을 검출하고, advisory lease는 충돌 가능성을 줄이는 보조 수단이다. MOESI는 설계 비유이지 CPU 캐시 일관성 프로토콜을 그대로 구현했다는 뜻은 아니다.

검증 가능한 성과와 한계

2026-08-10 고정 스냅샷 기준 compact overview 크기를 17,213B에서 1,886B로 줄였고, 결정론적 25개 질의에서 기대 경로 rank-1을 3/25에서 25/25로 개선했다. 단, 이는 고정 테스트이며 실제 상용 모델의 토큰 절감이나 전체 자연어 질문 성공률을 입증한 수치는 아니다. 자연어 검색 별도 15개 질의에서는 top-5 9/15, rank-1 7/15, 빈 결과 3개가 확인됐다.

AI 사용 원칙. 사람이 시스템과 근거를 이해한 뒤, AI는 탐색과 후보 생성에 사용한다. 코드·로그·실험으로 검증하지 않은 가설은 사실로 승격하지 않는다.
06 / Hardware & software

PYNQ / ZYNQ: 실제 주행의 마지막 단계에서 배운 것

PYNQ 보드와 DPU 기반 YOLOv3 Tiny, Python MMIO 모터 제어, 초음파 센서를 연결한 자율주행 프로젝트. 본선 주행 3위로 주차 단계에 진출했지만 대회 당일 주차는 실패했다. 초음파 raw 값이 약 600으로 지속되는 상황에서 타임아웃이 발생했다.

성공 사례만 남기지 않는 이유

사전 주행 성공 기록과 센서 dropout 기록, 대회 당일 실패는 서로 다른 증거다. 성공한 반복 테스트를 근거로 현장 조건에서의 안정성까지 과장하지 않고, 배터리 저전압과 센서 이상 등 미해결 원인을 구분해 남긴다. 이 경험은 센서 입력 검증, 상태 머신 복구, 실제 환경에서의 관측 가능성을 중요하게 생각하는 계기가 됐다.
